# RCA — расхождение цены 0593 (заказ ff1ead0c, 332 шт.)

Режим READ-ONLY: никаких изменений не вносилось.

## 1. Восстановление расчёта клиента
```text
unit price      = 290
quantity        = 332
subtotal        = 96 280
discount        = 5% → floor(4 814) = 4 814
customization   = нет (surcharge 0)
total           = 96 280 - 4 814 = 91 466  (точно совпадает)
```
Сумма сходится точно до рубля, и других комбинаций, дающих ровно 91 466 при 332 шт., нет.

## 2. Расчёт сервера
310 × 332 = 102 920; 5% = 5 146; итого 97 774. В сохранённом заказе: `pricing.source=server`, `baseUnitPrice=310`.

## 3. products.price_rub (0593)
**310 ₽**, `updated_at = 2026-10-09 07:39:47 UTC`. Цену меняли в админке за 4 минуты до заказа (заказ создан в 07:43:34). Для справки: старая `product_prices` = 270 ₽, P0 её больше не читает.

## 4. Snapshot в репозитории
`public/data/products-public.json`: 0593 → **290 ₽**, version `27c00555`, generatedAt `2026-06-10`. Он отличается от БД на 20 ₽.

## 5. Snapshot на продакшене
Проверить не удалось: адрес сайта на TimeWeb неизвестен, а по пробным адресам (giftastic-boxes.lovable.app, smtboxes.ru) файл не вернулся. Однако 290 ₽ у клиента однозначно совпадает со snapshot и не совпадает ни с одной цифрой в БД (310 / 270). Значит, клиент получил цену из snapshot. Чтобы это закрыть, нужен точный адрес сайта: тогда я покажу ответ сервера и заголовки кеша.

## 6. Путь цены у клиента
```text
products-public.json (290)
 → catalogFallbackService.toProductShape: price/price_rub = 290
 → productsService.getActiveProducts (JSON-first; Supabase только при ошибке JSON)
 → карточка / корзина: 290
 → pricingService.computeCart: 96 280 → 5% → 91 466
 → payload: subtotal 96 280, total 91 466
 → order-processing: products.price_rub = 310 → 97 774, priceAdjusted = true
```

## 7. Скидки клиента и сервера
Пороги (20/30/40/50 тыс.), проценты (2/3/4/5), порядок (сверху вниз) и округление (floor) совпадают. В обоих случаях скидка считается от subtotal до скидки. Расхождение вызвано только базовой ценой: и 96 280, и 102 920 попадают в ступень 5%.

## 8. Как обновляется snapshot
- Обновляется только вручную: `npm run export:catalog` → пересборка → загрузка `dist/` на TimeWeb.
- Нет триггера, вебхука, CI/CD, Edge Function и сброса кеша.
- Сохранение в админке snapshot не трогает. Продакшен продолжает отдавать старую цену до ручного экспорта и загрузки.

## 9. Root cause
**ROOT CAUSE CONFIRMED** (подтверждено для репозитория; ответ продакшена ожидает адреса сайта).

Подтверждена именно та архитектурная цепочка, о которой вы спрашивали:
1. В 07:39 в админке сохранили новую цену 0593: в БД стало 310 ₽.
2. Snapshot не обновился: в нём осталось 290 ₽ от июня 2026.
3. Витрина и корзина посчитали 290 × 332 с 5% = 91 466 ₽.
4. Сервер посчитал по 310 ₽ = 97 774 ₽, поэтому `priceAdjusted = true`.

P0 отработал правильно: сервер взял актуальную цену.

## 10. Варианты исправления (только описание, не применять)
- **A. Операционный, сразу:** после изменения цены выполнять `npm run export:catalog`, пересобрать и загрузить на TimeWeb. Сейчас нужно сделать это хотя бы один раз: в snapshot устарели как минимум 0593 и, вероятно, другие товары. Перед этим сверить все расхождения snapshot и БД.
- **B. Минимальный код:** витрина при загрузке подтягивает актуальные `price_rub` из `products` (одним лёгким запросом) поверх snapshot; snapshot остаётся для фото и структуры.
- **C. Корзина:** перед оформлением сверять цены с сервером и показывать клиенту новую сумму до отправки, а не после.
- **D. Позже:** админка после сохранения показывает предупреждение «нужно обновить каталог сайта» или автоматизирует экспорт.

Рекомендация: сначала A, затем B (либо C) отдельным согласованным P0.
